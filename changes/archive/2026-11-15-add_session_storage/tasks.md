- [ ] How a fork resumes has no clause: the copy lands uncommitted, so the fork's last turn is open and a next tool call writes into the copied turn under its old number, and readers see a complete turn as uncommitted. Measured: committing the copied turn with one extra event leaves the child's turn holding three events — the copied one and both re-passed ones — because `commit` writes the turn's whole event list.
- [ ] A fork copies payload bytes, and SQLite shares no stored content: 3000 turns with a 200-byte payload store in 1,032,192 bytes, and each full-range fork adds 970,752 (4 forks → 4.76×). The bundled SQLite is 3.54.1 (`libsqlite3-sys` 0.39.1's `sqlite3.h`), and it compresses nothing in the core — `sqlite.org/compile.html` (read 2026-11-14) lists zlib only for the SQLAR extension, and the vendored `sqlite3.c` names no zstd — while the only dedup it documents is a DELETE over duplicate rows ([database.guide](https://database.guide/2-ways-to-delete-duplicate-rows-in-sqlite/), read 2026-11-14). One source of truth for repeated payloads is therefore an app-level shape: `blobs (id INTEGER PRIMARY KEY, bytes TEXT NOT NULL UNIQUE)` referenced from `events`, written with `INSERT OR IGNORE`. Measured on the same rows: the session 163,840 bytes (6.3× smaller) and each branch 150,528 (6.4× cheaper) — the saving is the payload copy, so it is largest where payloads repeat. It is not free: `events.payload` leaves the table, so `events_fts` re-keys onto the blobs and R-session-10 becomes a MODIFIED clause. Not built here: no clause asks for it, and the copy keeps the log's per-session identity intact (`seq`, the composite FK, the append-only triggers, the index keyed by `rowid`). It is the shape every fork-like operation wants — a subagent fan-out, a user branch, a rollback, which the append-only log can only express as a fork to an earlier turn — so it opens as its own change with its own clause.

- [x] R-session-33: two processes opening a fresh store both open it. Setup runs at its own short `busy_timeout` (100 ms) and its two steps are retried — 20 attempts, 50 ms apart — because theirs are the refusals a busy handler cannot settle: the journal upgrade is refused the moment a lock stands, and the migrations run in a deferred transaction, which SQLite rolls back when it meets a lock, so the statement answers `SQLITE_BUSY` even after the busy handler has waited. The budget is therefore the tolerance: a setup absorbs a foreign writer for ~1 s (the upgrade leg) to ~3 s (the migration leg), where the 5 s timeout restored after setup absorbs ~101 s. `Store::setup_refusals` reports the refusals a setup waited out, so the scenarios measure a met lock instead of trusting a beat. Scenarios: a locking connection holds an open write transaction while a child (`crates/tau-test/src/bin/open_store.rs`) opens the same path — on a fresh file (the upgrade leg; witness: the mode reads `delete` under the lock), and on a file already in WAL (the migration leg; witness: `wal` under the lock and no `events` table), each ending with the file in `wal`. Mutations, each run: one attempt instead of twenty turns the upgrade leg red (`the second instance failed: open_store: sqlite: database is locked; the store on disk is in delete mode, expected wal`) and the migration leg red (`the second instance failed: open_store: migrations: rusqlite_migration error while executing query 'CREATE TABLE sessions (`); taking no lock turns all three red (`releasing the setup lock: cannot commit - no transaction is active` on the two legs that read the mode, `the store's tables were created while the lock was held` on the migration leg); cutting every beat to 0 turns all three red (`the second instance met no refusal, so the setup race was never measured`, and on the bounded leg `the second instance did not report a busy store: exit 0; opened refusals=0`); dropping the migration leg's WAL pre-set turns it red at its own premise (`the migration leg left the store in delete mode, expected wal`).
- [x] R-session-34: a setup lock that outlasts the budget is refused, not waited on forever: the scenario holds the lock for 3 s — past the ~1 s the upgrade leg spends, so the refusal lands ~2 s before the lock clears — and the child is refused with `sqlite: database is locked`. Raising the budget to 1000 attempts turns it red (`the second instance is refused with a busy store: the second instance did not report a busy store: exit 0; opened refusals=56`), so the refusal is measured, not assumed. The beat was 1.5 s, which left ~0.5 s of margin over the budget — enough for a loaded box to spend; 3 s is the margin, and the scenario is timed against the budget, not the machine.
- [ ] Two writers on one session are not refused, and no clause names a per-session writer: two processes committing the same `(session, turn)` collide on the primary key (the first state is kept, one event stored, no half-write), while commits of distinct turn numbers to the same session both land and interleave (100:A, 101:B, 102:A), which splits one model context across two agents. Measured with two processes on one store, 300 commits each: with `busy_timeout` 5 s, 0 failures and a worst commit of 41 ms; with `busy_timeout` 0 every write fails, so the timeout is load-bearing. The rule the store already offers for free is the existing primary key, surfaced as a named retryable error.
