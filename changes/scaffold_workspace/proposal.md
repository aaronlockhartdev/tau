# scaffold_workspace

## Context

There is no workspace manifest and no member crate: `crates/` holds `tau-test/tests/features/STEPS.md` and a `steps/` keep-file, and the root has no `Cargo.toml`. 13 of the 17 gate rows in `AGENTS.md` are cargo commands; the rest are the two doc gates, `git ls-files` and the toolchain file. Before this change 16 of the 17 report `skipped (M0)` and the `eval` row is `manual`, so no commit has evidence. `changes/add_session_storage/tasks.md` names the block ("blocked on the planned `scaffold_workspace`: no crates to own the schema yet"), and spec-change §4 states implementation is blocked until this change. `add_repo_layout` decided the tree (option A: virtual manifest at the root, `members = ["crates/*"]`, crate name equal to the directory), and `change_spec_requirements` owns those rules as R-workspace-01..05, accepted by the four layout-domain gates (`workspace layout`, `no local state tracked`, `contracts current`, `toolchain pinned`). The `spec` CLI that opens a change is one of the members the scaffold creates, so this change opens by hand from `changes/_template/`.

## Options

- A. Scaffold all six members as compiling targets, and land the four targets the gate rows name, in three of the crates: `tau-tools` bin `spec`, `tau-protocol` bin `contracts`, `tau-test` features target plus bin `steps`. Evidence: measured here — 17 gate rows in `AGENTS.md`, 13 of them cargo commands, and five rows naming four signatures: `-p tau-tools --bin spec`, `-p tau-protocol --bin contracts`, `-p tau-test --bin steps`, `-p tau-test --test features`; `add_repo_layout/proposal.md` records the cucumber-rs feature path resolving from the crate root as `unverified` "until the first `scaffold_workspace` task runs a stub feature". Cost: `cucumber` 0.23 as a dependency of `tau-test` (the step definitions live in its lib) and `tokio` as a dev-dependency, `gherkin` transitive through `cucumber`, 0 dependencies in the other five members, the `tau-app` stub bin with an empty `[dependencies]`, one cold workspace build.
- B. Root manifest and `tau-core` only. Evidence: measured here — the `no local state tracked` and `toolchain pinned` gates pass with a `.gitignore` and a toolchain file, and R-workspace-04's `contracts current` gate needs the `contracts` bin. Cost: the `workspace layout` gate compares the manifest members against the six-crate list in `docs/stack.md`, so one member fails it; the `spec tool`, `spec lint`, `contracts current`, `steps current`, `behaviour` and `workspace layout` rows stay `M0`, so the next change opens by hand again and the feature tree's location stays open while scenarios are written against an unverified path.
- C. One crate, modules only, and the `apps/`/`libs/` split. Evidence: ruled out in `add_repo_layout` options C and D — a module cannot declare dependencies, so nothing stops a `tau-app` import inside core. Cost: the core-decoupling gate loses its proof.

## Decision

A: the tree `add_repo_layout` decided, as compiling targets, with the four tool targets that make the gate rows run, in three of the crates.

Consequences:

- This change owns no new rule. Every obligation it implements is a clause in another change's delta, cited by ID in `tasks.md`: R-workspace-01..05 (`change_spec_requirements`), R-harness-01..03 (`change_spec_requirements`), R-harness-04 (`add_test_lanes`). R-workspace-03 (`target/` and `.tau/` out of git) is met by the root `.gitignore` that predates this change; its acceptance ref is the `no local state tracked` gate, and the stub feature tags the same fact. It carries no `specs/` of its own, the way `add_repo_layout` and `spike_gpui_surface` do not, and no change archives with it.
- `spec new` copies the template's placeholder deltas, whose `### R-<domain>-<NN>` headings are placeholders, not IDs, so `spec --check` skips any path with a `_template`, `_domain_` or `_area_` component: a freshly opened change lints clean before it is edited. This is the read-side detail R-harness-01,02 (`change_spec_requirements`) leave open.
- `AGENTS.md` gate rows flip from `M0` to `run` for the rows this commit makes green, twelve of them: spec tool, spec lint, contracts current, doc lint, links, unit + surface, behaviour, steps current, no local state tracked, toolchain pinned, core has no UI logic, lints. `workspace layout` does not flip: its rule is the manifest members against the crate list in `docs/stack.md`, and `gates` runs a row's first command span only — `cargo metadata --no-deps`, which compares against nothing — so as a `run` row it would always pass, and the row stays `manual`. `live output under load`, `headless session` and `desktop` stay `M0`: the spike owns the frame budget, and the tape runner and the GPUI surface do not exist.
- `run` reports what the command does, not that every clause behind the row has tests. `unit + surface` runs nextest, which has the unit tests and no surface-lane test — that lane is R-harness-06 (`add_test_lanes`). `spec lint` passes on this commit: the tools domain's hole at `R-tools-14` — a clause `07a2ab6` issued and `af434fe` deleted — was closed by shifting the two unimplemented changes above it down one, so skills now runs 14..21 and editing 22..29, legal under spec-change: a delta clause no scenario has run yet renumbers inside its own change.
- `tau-app` carries no GPUI dependency in this change; `spike_gpui_surface` adds `gpui-kit` and measures it, so the `desktop` row stays `M0` and the app crate is a stub bin. Its command runs — the stub prints one line — but the row proves a desktop surface, which the spike owns; `unit + surface` is nextest, and it runs the unit tests of the scaffold.
- `tau-test` gains no `bin mock-llm` and no `bin eval`: the tape that drives the behaviour lane is R-harness-05 (`add_test_lanes`), and no clause owns the `suites/` tree yet — `add_session_storage` R-session-13 only states what an eval harness must answer once one exists — so the `eval (never CI)` row stays `manual` and `crates/tau-test/suites/` is not created.
- The features tree lives at `crates/tau-test/tests/features/`, and the stub feature is the measurement of the cucumber-rs path claim; if it resolves from the crate root as `add_repo_layout` expects, the claim closes and every later scenario is reachable by `cargo test -p tau-test --test features`.
- `contracts/` gains no schema file: `tau-protocol` has no wire type yet. The directory rides on the tracked `contracts/.gitkeep`, so `contracts --check` compares an empty generated set against it and passes; with an empty generated set the write mode deletes nothing, and it reports a schema that is on disk ungenerated, unreadable, or not committed.
- The features target answers `--list` with no test names, because cucumber is not the libtest harness. Measured here: with that answer `cargo nextest run` runs the unit tests; without it nextest runs the lane binary with `--list`, the binary exits on `unexpected argument '--list'`, and the `unit + surface` row fails before the unit tests run. The lanes stay split as `add_repo_layout` drew them: nextest runs unit and surface, `cargo test -p tau-test --test features` runs the scenarios.
- `gherkin` stays transitive through `cucumber`; nothing in this change imports it, so `docs/stack.md`'s pin pair is untouched and the direct dependency lands with whichever clause first names gherkin.
- `cargo run -p tau-tools --bin spec -- count` is now a command, so `spec/index.md` drops its "manual until M0" note. The `doc lint`, `links` and `unit + surface` rows run binaries outside the workspace (`rumdl`, `lychee`, `cargo nextest`, all named in `docs/stack.md`); a checkout without them fails those rows.
- Upkeep: six member manifests, each with `[lints] workspace = true`, and one dependency list at the root; a new member needs only a directory under `crates/`.

Eval: none needed.

Open: none.
