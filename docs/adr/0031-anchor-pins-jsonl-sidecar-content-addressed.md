# Anchor pins are persisted in a JSONL sidecar, content-addressed by line checksum

**Status**: **superseded by ADR-0032** (2026-10-20) — the pin store moved to a per-workspace SQLite file with session-start GC. Accepted 2026-10-19 (the pinning-store half of issue #207, hashline v1).

The hashline anchor system (spec §5.4, ADR-0030) allocates anchors per read. The in-memory registry (the prerequisite cluster, landed) is session-scoped: a line's anchor is stable while the session is alive, but a new session re-mints from a global probe cursor, so the *same* line gets a *different* anchor in the next session. That is the churn source the pin store closed — now retired as a necessity: ADR-0033 made the registry's allocation itself content-addressed, so a fresh session over identical content re-derives the same anchors without any store, and the store's remaining value is the cache role (tombstones, changed-line history, drift detection) ADR-0032/0033 describe.

**Decision**: a persistent **pin store** closes that gap. A file's anchors are *pinned* — stored per workspace at `.tau/anchors/{xxh3-64(path)}.jsonl`, one CRC32-guarded JSON record per file (`{path, checksum, line_count, pins, crc}`, the session-store format of ADR-0005). A pin is **content-addressed**: it ties an anchor to the line's *checksum* (xxh64 of the canon), not to a line position. On a file's first read in a session, the registry seeds from the store: the stored pins are the "previous allocation" the LCS-over-checksums re-anchor matches against, so a line unchanged since the last session keeps its exact anchor. After each edit the refreshed pins are persisted (survivors keep their anchor, changed/new lines take the fresh anchor, deleted lines' slots are **tombstoned** — kept and flagged, never recycled for the record's life). A `write` drops the record. The store is best-effort: a load/verify/save failure degrades to the in-memory registry path (fresh allocation) and never fails the tool.

> **Amended 2026-10-27 (#304)**: a `write` **retires** the record — every slot is tombstoned and the row stays. ADR-0033 made content-addressed allocation self-deriving, so the store's remaining purpose is the tombstones, and a `write` that deleted the row was handing freed anchors back to the next session. The mint refuses a retired anchor for the store's life, and for the rest of a session whose retire did not persist.
>
> **Amended 2026-10-27 (#310)**: "for the record's life" is now bounded. A record carries at most `MAX_TOMBSTONES` retired slots, capped on the way to disk, oldest claims first out: a file edited every day appended the slots it freed on every generation, and its row — refreshed by each retire, so invisible to the retention sweep — grew without limit. Past the cap the oldest freed anchors become mintable again, which this ADR always allowed: the store is a cache, correctness never depends on it, and the session that freed them keeps every claim. The one case the ownership gate does not catch is a line deleted and re-added with identical content after its slot was dropped: it re-mints the same content-addressed anchor, and the integrity check passes.

**Store technology** (full analysis in `docs/research/anchor-pin-store.md`): JSONL, not SQLite. The workload (one KB-range record per file, whole-record load per session, a small write per edit, no cross-file queries, one process per workspace) is a strict subset of the session store's, and JSONL is what won that analysis on crash-safety (atomic temp+rename), debuggability (human-readable), and zero new dependencies. The reference fork's SQLite store (WAL, busy-retry, corruption quarantine, cross-file snapshot index) solves problems this workload does not have, at the cost of a C-compiled binary dependency.

**Considered**: SQLite — rejected (no efficiency gain at this scale; binary dep; the cross-file query capability is unused). Position-addressed pins (anchor tied to line number) — rejected: that is exactly the churn being eliminated; a one-line insert shifts every position after it. A per-workspace single `anchors.json` — rejected: it serializes every file's edit behind one file lock and rewrites the whole workspace's pins on every edit; per-file sidecars make the write O(one file) and the crash domain one record.

**Consequences**: `Registry::with_store` is the constructed path (the session builds it from the workspace `.tau` dir); `Registry::new` (no store) remains for tests and the ACP path. The pin store is a new `hashline/pin_store` module (self-contained CRC32 + atomic write, re-implemented from `session/entry.rs` rather than shared, to keep the module independent). The store is an anchor-stability optimization: correctness (stale-anchor rejection, the integrity check) is unchanged and never depends on the store. A line that is deleted and later re-added with identical content gets a *fresh* anchor (its old slot is tombstoned), not the old one — a deliberate cost of tombstones over recycling.
