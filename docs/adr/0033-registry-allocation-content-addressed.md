# The registry allocates anchors content-addressed, not from a global probe cursor

**Status**: accepted (2026-10-20) — issue #239. Completes the cross-session stability story ADR-0031/0032 started.

ADR-0030 made the *pure* allocator content-addressed: a line's base slot is `xxh32(hash_source) >> 14 % 52⁴`, with stride probing on collision. The session registry — the actual tool path (`read`/`edit` are registry-driven) — still minted from a **global monotonic probe cursor** shared across files. So the anchors the model saw were a function of *allocation history*, not content: two fresh sessions over identical files minted different anchors, and the pin store (ADR-0032) was the only thing keeping a line's anchor stable across sessions. The reference implementation (pi-hashline-edit-pro) allocates content-addressed in the registry too.

**Decision**: `Registry::allocate` mints content-addressed. A line's first mint starts the probe at its content-derived base slot (`line_base_idx`, the helper ADR-0030's allocation already shared) and walks forward by stride — against the registry's **global** `owned` set plus the current read's `fresh` mints (uniqueness is session-wide, and a same-content pair in one read must not double-mint the base; the per-read set is the registry's mirror of the pure path's per-file bitset). When the base is occupied, the walk starts at the file's running hint (a per-file `file_hint` mirror of the pure path's running hint), then at the global cursor — which now only serves as a fallback. A mint advances `probe` past the slot it took, so a fallback mint never re-lands on a fresh base. Two fresh registries over identical content therefore allocate identical anchors, with or without the pin store.

**Considered**: keep the cursor for cross-file mints — rejected: that is exactly the churn this removes, and it made the pure-path `line_hashes` and the registry's allocation disagree on identical content (a latent inconsistency: a re-read after `free` would re-derive different anchors). A global `everMinted` set (the reference's) — rejected: it would permanently burn slots across re-reads and reclaims; the `fresh` per-read set plus the live `owned` set gives the same collision protection for the window where a double-mint is possible.

**Consequences**: cross-session anchor stability no longer *depends* on the pin store — the store becomes a pure cache (it still wins when present: a pinned anchor is exactly the content-derived one for an unchanged line, and tombstones/changed lines are where it adds value). The acceptance-tools fixture re-pins to the computed anchors (`line1` = `BdoD`, `line2` = `BiOm`; the fixture's edit now targets `BiOm`). One-time break: sessions started before this change show anchors the new allocator will not re-derive until a `write`/re-read — same class as the ADR-0030 format break, no migration. The monotonic cursor is kept (fallback only) because a mint with no line content must still allocate somewhere, and slot 0 stays untouchable.
