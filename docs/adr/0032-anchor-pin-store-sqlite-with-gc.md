# The anchor pin store is a per-workspace SQLite file with session-start GC

**Status**: accepted (2026-10-20) — supersedes ADR-0031 (JSONL sidecar). The pin-store half of issue #207, escalated per the trigger ADR-0031 named.

ADR-0031 stored a file's pinned anchors as one CRC32-guarded JSON record per file under `.tau/anchors/`. It served the hashline anchor system (spec §5.4, ADR-0030) well at small scale, and it named its own escalation triggers: *the record count outgrows directory-listing cost*, or *a corruption mode appears that CRC32 + atomic rename does not cover*. Both are now live. The store is append-only in effect — a `write` drops one file's record, but records for files deleted from disk, moved, or never again read accumulate without bound — and the per-file CRC32 cannot detect a torn *database* (a half-migrated or half-written store file). The decision to move the pin store to a database is made; this ADR records the technology choice and the new lifecycle behavior. Full analysis in `docs/research/anchor-store-db-migration.md`.

**Decision**: one **SQLite** file per workspace at `.tau/anchors.sqlite` (driver `rusqlite` with the `bundled` feature — the only new dependency). The store's public API does not move: `new`, `file_path`, `load`, `save`, `remove`, `paths` keep their signatures; only the serialization behind them changes (a `pins` JSON blob column instead of canonical-JSON + CRC over the whole record). `file_path` now returns the single db file; `paths()` is `SELECT path FROM anchors`. The schema is one table `anchors(path TEXT PRIMARY KEY, checksum, line_count, pins TEXT, updated_at INTEGER)` plus a `meta` table carrying a `version` row.

**Why SQLite over the alternatives** (research doc §2): the reference fork's store is SQLite, and its machinery is exactly the design we want to inherit — WAL + `synchronous=NORMAL` for crash safety, `secure_delete=ON`, `auto_vacuum=INCREMENTAL` with an opportunistic `incremental_vacuum` when the freelist passes 20% of pages, `busy_timeout` retry, `PRAGMA quick_check`-gated corruption quarantine (rename db + `-wal` + `-shm` to `*.corrupt-{ts}-{pid}-{rand}` and rebuild), and a `meta` version row with nuke-on-mismatch. `bundled` compiles SQLite into the build (no system `libsqlite3`). **`redb` 4.4.0 is the documented fallback** if review re-weights dependency-minimalism over mechanism-inheritance: it is a legitimate pure-Rust KV that serves this one-table workload, but porting the fork's corruption/quarantine/vacuum story to redb's non-SQL API surface means re-deriving machinery that already exists.

**Garbage collection** (research doc §4), run at session start, best-effort, before any tool call: (1) a **missing-file sweep** (always on) that stats the rows' paths in batches of 64 and deletes the rows whose file is gone — this alone is a pure win at any scale, since the store is unbounded today; (2) an **age expiry** (config-gated) that deletes rows older than a retention window; (3) the opportunistic vacuum. Neither sweep may fail the session — a sweep error is logged and the session proceeds (the store is a cache).

**Configuration** (research doc §5): a new `[hashline]` section in the existing TOML system (`config.rs`, spec §12 layering) — `retention_days` (default 180; `0` disables age expiry, the missing-file sweep always runs) and `gc_on_start` (default `true`). It reaches the session through `SessionParams` (built in `harness/launch.rs`), which already carries the other config-resolved settings (`gates`, `om`, `tool_batch_on_force`); child sessions inherit it via the `Supervisor` → `Inherited` bundle, mirroring the `om`/`gates` pattern. `agent.rs` passes it to `PinStore::new(root, GcPolicy { … })`. The ACP path's `Registry::new` (no store) is untouched.

**Considered**: `redb` — the pure-Rust fallback (above). JSONL (status quo) — retired: unbounded growth, no corruption detection for a torn store. One big `anchors.json` — rejected again (ADR-0031's reasoning stands: it serializes every file's write behind one lock and rewrites the whole workspace on every edit). A per-pin table — rejected: the access pattern is whole-record-only (the registry seeds a file's *entire* previous allocation for the LCS re-anchor), so a per-pin table only adds write amplification; `pins` stays a JSON blob.

**Consequences**: a new binary dependency in every build (bundled SQLite, ~1 MB) — accepted, it buys the crash-safety and corruption-detection that motivated the move. Debuggability drops from "open a human-readable JSON file" to "run a sqlite3 CLI on the file"; the `pins` column keeps the per-record content at least `sqlite3 .dump`-able, and the record is an optimization, not a source of truth. WAL sidecar files (`-wal`, `-shm`) appear under the workspace's `.tau/` dot-dir; the quarantine path handles all three. The `FilePins`/`Pin` types, the re-anchor/tombstone semantics, and the best-effort degradation (any store error → in-memory registry path, never fail the tool) are all unchanged. The legacy JSONL sidecar is dropped outright — there is no import path (a scope decision for this ticket); a stale `anchors/` directory is simply no longer read.
