# OpenAI-compatible providers only in v0

Pi ships a catalog of ~20 providers with OAuth subscriptions and API keys. Tau v0 supports only OpenAI-compatible endpoints (base URL + key + model id), which covers OpenAI, OpenRouter, Groq, Ollama, llama.cpp, vLLM, and similar servers. Rationale: one API surface keeps the core minimal (a standing "lightweight" preference); the catalog, OAuth, and subscriptions can be added later without re-architecture. The exact contract is settled on the map (ticket #7). **Endpoint surface (2026-09-16, user decision, revised same day): v0 speaks `responses` only — no `chat-completions` implementation in v0.** OpenAI/OpenRouter/vLLM are native; llama.cpp is reachable via its `/v1/responses` shim; Ollama's non-stateful `responses` is fine (tau is client-side stateful). Per-server fidelity is the **user's responsibility** in v0 — no auto-detection, no per-provider profile config; a `chat-completions` fallback is a post-v0 addition for servers whose `responses` is insufficient.

**Considered**: multi-provider catalog with OAuth in v0 (pi parity). Rejected: it is the heaviest part of pi, and it is not what "lightweight" means here. Also considered: chat-completions-first, the research #4 recommendation, on uniformity grounds. Overridden by the user: the newer `responses` API is the direction for v0. **Revised 2026-09-16 (user): the per-provider chat-completions fallback is out of v0 — v0 is responses-only; the fallback moves to post-v0.**
