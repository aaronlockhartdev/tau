# tau v0 — Specification

**Status**: draft for user review (the #12 capstone deliverable) · **Date**: 2026-09-17
**Provenance**: synthesized from the wayfinder map [aaronlockhartdev/tau#1](https://github.com/aaronlockhartdev/tau/issues/1) — every decision below cites the ticket that settled it and, where one exists, the ADR that records it. Terms follow [`CONTEXT.md`](../CONTEXT.md). Items the map has **not** settled are marked **UNRESOLVED** and collected in [§14](#14-unresolved-index); there are no silent defaults.

**How to read this**: §1–§2 are the frame; §3–§8 are the core (what `tau-core` must implement); §9 is the renderer (what the Svelte/Tauri GUI must present); §10–§13 are the surrounding decisions; §14 is the open list. Ticket numbers refer to the map's issues.

## 1. Scope

**In v0** (settled at charting, #1):

- An agent loop with the four pi tools: `read`, `write`, `edit`, `bash`.
- Streaming chat over a single OpenAI-compatible endpoint surface.
- Context files + system prompt (pi's pattern, 2026-09-17).
- Three message lanes: **force / steering / follow-up** (§7).
- Tree sessions with in-place branching (§3).
- **OM-based compaction** — Mastra's Observational Memory — as the *only* compaction mechanism (§4, ADR-0004).
- **Native sub-agents + task hand-off** as core primitives (§5, ADR-0001).
- **OpenAI-compatible providers only** — `responses` endpoint exclusively (§6, ADR-0003).
- **One Tauri process with a standalone core library** (§2, ADR-0002).
- The **GUI**: chat always central with a focus mode; open workspaces as top tabs; left pane tabbed `files` | `sessions`; right pane tabbed `tasks` | `sub-agents`; vertical steering queue; lualine-style status bar; markdown + syntax highlighting (§9, #11).
- A **core↔GUI protocol** that is a transport-agnostic message set (§8, ADR-0006, #10, #13).

**Not in v0** (pi features deliberately deferred, #1): extensions, skills, prompt templates, themes, the pi-package ecosystem, OAuth + provider catalog, plan mode, CLI/print/RPC modes, project-trust flow, telemetry. Additionally settled out-of-scope during the map:

- **Mid-turn human-in-the-loop** — no permission popups, no confirmations. The model asks questions by *ending its turn* with a question message; the user answers in the composer (#10). The protocol keeps the HITL request/response *shape* (pair + timeout + queueing) with **zero live request types**; a future security ticket decides what comes back (#13, #10).
- **Protocol version field** — pre-v1 is breakable; versioning is added before v1 (#10).
- **The `tau serve` network binary, auth/TLS, multi-client policy, session sync** — legitimate deferrals that the §8 constraints keep cheap (#13).
- **Vector-search `recall`** — v0 `recall` is browse-only; a `search` mode is a designed-in extension (ADR-0004).
- **Windows** — macOS first, Linux second (§13).

## 2. Architecture

(ADR-0002, #1, #10)

- **One Tauri process.** The agent runs in the Tauri main process: a Rust core owns the loop, sessions, and tools; Svelte is a thin renderer over Tauri commands/events. No separate agent binary in v0.
- **`tau-core` is a standalone library crate.** All stateful logic lives there, free of Tauri types (enforced in review — it is the whole bet that a future `tau serve` binary is a transport shim, #13/ADR-0006). The library boundary preserves the CLI/RPC/serve options pi's SDK/RPC separation offers, without paying IPC cost now.
- **Rejection on record**: a separate agent binary over stdio/IPC (pi's RPC pattern) — one process is simpler for v0; the library boundary keeps the door open (ADR-0002).
- **Dependency surface** (standing lightweight preference: single binary, minimal deps): `reqwest` (rustls), `serde`/`serde_json`, `tokio`, `bytes`, `xxhash-rust` (hash-anchored `edit`, §5). The SSE parser is in-tree (~100 LOC, #4). Nothing else.
- **Execution model**: in-process concurrency — a sub-agent is a concurrent agent-loop instance inside `tau-core`, not a child process (#6; ADR-0001 supplement). One core serves all workspaces/sessions/sub-agents of the running app; per-session single-writer is the concurrency rule (research #5 single-writer default).

## 3. Session storage

(research #3 → user ratification 2026-09-16 → ADR-0005)

**Decision: keep the pi-style JSONL family, hardened in three ways.** Measured on a ~1 GB corpus of 280 real pi sessions (1.1 KB → 85 MB): no candidate encoding beats JSONL *across the ticket's dimensions* (MessagePack/CBOR save only 4–14% overall, shrinking to ~7% on payload-dominated sessions; the size headroom is in the *payload* — base64 images were 40.4% of the largest session — not the encoding), and every alternative loses human readability, which the ticket weights for a dev tool.

- **One file per session**, `grep`/`jq`/`vim`/`diff`-able. First line is a header (includes a **file-format version** — the session file is a separately versioned surface from the protocol, pi-style); every subsequent line is one entry `{type, id, parentId, timestamp, crc, …}`.
- **The tree is `id`/`parentId`**; the leaf is the current position. **Branching = appending a new child line** pointing at any earlier entry — never a file rewrite. A session has exactly one active branch at a time (#10).
- **Compaction/OM records are appended entries referencing the replaced span** (pi's `firstKeptEntryId` pattern, extended with the richer OM payload; §4) — append-only, audit-friendly, no in-place rewrite. Pre-compaction entries stay on disk.
- **Hardening 1 — per-line `crc` field** (measured +0.2–0.3% of file size): detects silent mid-line corruption that parse-or-skip cannot. Crash safety: kill-safe by construction (line framing + load-time repair of a torn last line); power-loss durability is not a v0 requirement.
- **Hardening 2 — out-of-band sidecar blobs** for payloads above a size threshold (measured: 83 lines >100 KB, max 1 MB, mostly base64 images): stored as raw-byte files (removing base64's 33% expansion), zstd-compressed, referenced by id from the entry. The log stays readable; the worst-case single write shrinks; tail reads stay cheap.
- **Hardening 3 — manual archives** (explicit user action — the GUI; **no auto-archiving, no auto-compression, no cleanup schedule**): a session file is zstd-compressed into `archive/` and removed from `sessions/`; un-archiving decompresses it back. One-way per action, off the live read/write path — captures the measured 3.4× reclamation (zstd -3 on a 48.9 MB session → 14.2 MB) on demand.
- **Placement** (user-confirmed 2026-09-17): workspace-scoped session data lives in the workspace's project directory — **`{project root}/.tau/sessions/`** (one file per session, sidecar blobs in `blobs/`, manual archives in `archive/`) — alongside the per-workspace task store at **`{project root}/.tau/tasks/`** (§5); sessions with no project live in **`~/.config/tau/sessions/`**. Placement is a **core-side rule**: on a remote backend the files live on the host where `tau-core` runs (no local paths as identity, #13).
- **Revisit triggers** (ADR-0005): sessions routinely >~100 MB, multiple processes writing one session file, or structured queries across many sessions → SQLite (WAL) or a segmented log become worth revisiting. Rejected on the record: MessagePack/CBOR, SQLite WAL, segmented LevelDB-style log, whole-file/segmented zstd (breaks appendability and crash safety).

## 4. Compaction: Observational Memory

(research #2 → #9 → ADR-0004)

**OM is the compaction** — there is no pi-style one-shot summarization path. An **Observer** LLM converts raw messages (including tool calls/results) into a dense, append-only, date-grouped, emoji-prioritized observation log; a **Reflector** LLM periodically rewrites the log itself to keep it bounded; the live context is always **observations block + recent raw window**; raw messages remain in storage and are recoverable.

- **Per-session `OmRecord`** — observations text, **path-scoped cursor** (entry-id + timestamp), generation counter, token accounting — stored in the session as appended entries (ADR-0005 carries the record).
- **Observer** fires at **turn end** when unobserved tokens ≥ threshold (**default 30k, configurable**) and no tool batch is in flight. It appends after a `--- message boundary (ISO) ---` delimiter (cache stability), prunes observed entries from the next request (same cut rules pi enforces: never split a tool call from its result, cut at entry boundaries), and injects a continuation hint so the model doesn't react to history vanishing.
- **Reflector** fires when observations tokens ≥ threshold (**default 40k, configurable**): it rewrites the *entire* observation log (draw connections, drop redundancy, condense older entries more aggressively, preserve ✅ completion markers and user assertions) and commits it as a **new generation**. If the output isn't smaller, an escalating **compression ladder** (4 levels, ending in outcome-only tool observations) retries.
- **The ported dynamic threshold is the overflow guard**: raw history oscillates between a retention floor and the threshold (defaults: ~6k ↔ 30k; the observation log bounded ~40k), so two independent budgets never overflow — no second emergency mechanism.
- **Async buffering is in v0** (user chose Phase 1 + Phase 2 of the port plan, #9): fire-and-forget Observer runs over the *safe completed prefix* in **~6k-token increments**; activation at threshold or idle **requires no LLM call** (promotes buffered chunks, prunes raw to the floor). v0 uses a fixed idle timeout, not provider-cache-TTL auto-mapping.
- **`om_model`**: a single **global** config value (user decision 2026-09-17 — not per-provider), defaulting to the session's own model — a cheap model can serve both Observer and Reflector.
- **Per-branch records** (tau's addition — Mastra has no branch concept): forking copies the parent's `OmRecord` (observations + cursor) at the fork point; each branch then observes independently, with the cursor always evaluated on the active path.
- **`recall` tool** (in v0, child and parent sessions): page from an observation group's `range="startEntryId:endEntryId"` back to raw session entries — **browse-only, no vector search**. Designed-in extension: groups carry stable ids + ranges, so a later `search` mode = embeddings config + index sidecar, no schema change.
- **Prompts and threshold math are ported verbatim from Mastra** (Apache-2.0; the ported files sit outside the separately-licensed `ee/` directory; attribution at the port site).
- **Consequence on the record**: OM's published evidence (LongMemEval 84–95%) is for long-conversation *recall*, not coding-task fidelity. v0 must measure **rework rate / token spend / cache-hit rate** before and after, and the recurring Observer/Reflector LLM cost is real (mitigated by a cheap `om_model` and ~10k-token tool-result truncation before the Observer sees results).

## 5. Sub-agents and tasks

(research #5 → #6 → ADR-0001 supplement → #10 refinements)

### 5.1 The sub-agent entity

- A sub-agent is a **concurrent agent-loop instance in `tau-core`** (in-process, not a child process — #6) with **its own session file** (placed with the parent's, §3) **linked to the parent** by parent session id + originating tool-call id. A child session is an *ordinary session* — openable in a tab, steerable, branchable, forkable in the GUI (#10); “child” is a link attribute, not a kind.
- **Context modes** (chosen explicitly per delegation; `fresh` is the default, user-confirmed): **`fresh`** — self-contained brief + the child type's own system prompt + context files, no parent history; **`compacted`** — the parent's OM observations + recent raw window + a `recall` tool scoped to the parent session; **`fork`** — a branched copy of the parent's history (and its `OmRecord`, §4).
- **All spawns are asynchronous**: `subagent_spawn` returns an **opaque handle** immediately; completions are **pushed to the parent as events** (the result is injected at the parent's next turn boundary). A running child cannot be resumed.
- **Hand-off**: brief *in* (goal, context pointers, constraints, output schema); out = a **schema-validated `parent_notify {done: true, output}`** tool call. The child's output is **marked untrusted** before the parent's model reads it (research #5 inbound boundary).
- **Two-way messaging**: a *running* child receives parent messages on its **steering lane** (`subagent_message`); a *paused* child is **resumed by a message** (`subagent_resume {message}`). A parent has **no force** over a child (user-only capability — the composition `subagent_stop` + `subagent_resume {message}` achieves the effect without a blind mid-stream kill, #10). `subagent_state {handle}` gives structured inspection: status, last message, task + resume contract, usage, session pointer.
- **Caps** (config-driven, defaults decoupled from any specific local model, #6): **concurrency — default unlimited**; **depth — default 1** (a sub-agent cannot spawn sub-agents; at the limit the spawn tool is withheld, research #5).

### 5.2 Lifecycle (5 states, #10)

`running` · `idle` (with explicit `waiting_on: parent | user | subagent`) · `done` · `failed` · `stopped` (provenance: user or parent)

- **One-shot nudge**: if a child's turn ends without `done`, the core injects one nudge (“if done, call `parent_notify` now; if parking, state what you are waiting for”). The next turn-end yields a three-way fork: **done** / **valid idle declaration** → `idle` with `waiting_on` / **neither** → **`failed`** (one nudge per parked state — no loops).
- **`done`** = `parent_notify {done: true, output}`: `output` is required and **schema-validated by the core**; the core **auto-terminates the child's agent loop** (quiescence, not death — a done child is resumable like any other); the parent is **woken always** (the result is the wake).
- **`failed`** = nudge-exhausted or process/provider fault: **auto-notifies the parent to investigate** (read session, resume with a corrective message, reassign, or stop).
- **`stopped`** = soft interrupt by the user (GUI) or the parent (`subagent_stop`): the in-flight LLM stream is killed, the partial is kept as an **interrupted entry**, and — if a task was assigned — the **task's current resume contract** rides along in the stop event. *There is no synthetic LLM summary: the paused child's session file is the record.*
- **Wake rules**: `done` → parent woken; `failed` → parent notified; `idle, waiting_on: parent` → parked parent woken (the child names exactly the input it needs); `idle, waiting_on: user` → **GUI badge only**; `idle, waiting_on: subagent` → no parent wake (that child's own events do it); `stopped` → no parent wake. A child's done/notify **can wake a user-stopped parent** — stop means “interrupt current work,” not “never wake me” (enables *stop and wait for sub-agents*); a wake is a new turn the model can no-op, and v0 has no rate limit on notification wakes.
- **Resume — the only invariant is that nothing auto-resumes anything.** All non-running states (`idle`, `done`, `stopped`) are **deliberately resumable by both the parent (tool call with a message) and the GUI**; every resume is a deliberate act. (This abolishes the earlier #6 rule that user-stopped children refuse auto-resume; a hard lock, if ever wanted, is a separate explicit flag.)
- **Parent teardown**: closing a parent session **soft-stops all its live children** (no work runs for a session that no longer exists); a *deleted* parent's children become **standalone sessions** (parent link nulled, surfaced in the GUI as ordinary sessions); any task assigned to an orphaned child **stays in the task store as `in_progress` with its resume contract intact**.

### 5.3 Tasks

- A **separate first-class primitive**, distinct from sub-agents (user-confirmed; ADR-0001): a task is **state, not an agent** — completable by the **parent directly or by a sub-agent**; *assigning* a task to a sub-agent = spawning one whose brief is the task.
- **Per-workspace, event-sourced** store (`{project root}/.tau/tasks/`, §3): tasks outlive the sessions that work them; mutations are appended events (ADR-0005 consistency); replayable; the snapshot is the **resume contract**. The assigned sub-agent's session is linked to the task; the GUI task panel **spans sessions** (#10).
- **Enforced state machine** (core-enforced small enums — the only enums the model ever sees are these): **task** `pending → in_progress → done`, plus `blocked` / `cancelled`; **step** `pending / active / done / skipped`; **criterion** `pending / satisfied / failed / skipped`.
- **Steps**: an ordered plan, each step carrying an **expected output**.
- **Acceptance criteria** and **evidence-gated completion**: a task reaches `done` only if **every criterion is `satisfied` by passing evidence** — evidence items are `{criterion, summary, command?, artifact?, passed?, step?}` linked to a criterion, with a **`passed` boolean** and *no category enums* (the GUI derives display categories from shape; the rigor is in the wiring, not labels — #10). Escape: **force with reason**.
- **Blockers**: free text — `task_block {id, reason, needs?}`; no classification.
- **Decisions ledger**: `{question, decision, decided_by: user|agent, rationale}`.
- **Resume contract** — the compaction-safety device: current state, current step + expected output, evidence so far, gaps, blockers, next action. **When a session holding an active assigned task compacts, the task's current resume contract is re-injected after the compressed span on every compaction** — a sub-agent never loses sight of what it is doing. Context assembly is then: system prompt + observations + recent raw + (if assigned active task: resume contract).
- **`done` resolution gate**: a child with an assigned task that calls `parent_notify {done: true}` must resolve the task as **`completed`** (gate passes) / **`handed_off`** (stays `in_progress`; the output is the resume contract; the parent decides) / **`blocked`** (with reason) — a child can never silently exit with a task dangling `in_progress`, and is never trapped if it cannot finish.

### 5.4 The model-facing tool set (18 tools, #10 final)

| Group | Tools |
|---|---|
| Core (4) | `read`, `write`, `edit`, `bash` |
| Parent-side sub-agents (5) | `subagent_spawn`, `subagent_message`, `subagent_stop`, `subagent_resume`, `subagent_state` |
| Child-side (1) | `parent_notify {text, done?, output?}` (with `done: true`, `output` is required and schema-validated) |
| Memory (1) | `recall` — available in **all** sessions (parent and child); scope: the session's own raw entries, plus the parent's raw entries in `compacted` mode |
| Tasks (7) | `task_create`, `task_assign`, `task_start`, `task_evidence`, `task_block`, `task_finish`, `task_cancel` |

*Not tools*: asking the user (the model ends its turn with a question, §7); force-messaging (user-only, §7). Agent types (§5.5) can restrict the tool set per type.

**`read`/`edit` are hash-anchored** (the SOTA from research — “The Harness Problem,” +15 pts over patch across 16 models; the pi-better-edit scheme): `read` returns lines as `HASH│content` (3-char hashes from a 62-char alphabet — 238,328 space); `edit` targets `{from, to}` as hash anchors. Uniqueness is **allocated**, not hashed: a per-file bitset over the full hash space with collision probing (stride 3847), so an anchor is unique in its file by construction; canon = whitespace-stripped (reformatting never invalidates); survivor hashes are reused across edits (stable identity); deleted lines are tombstoned; stale/ambiguous anchors are **rejected, never fuzzy-matched**; a 238k-line hard limit falls back to `write`. Port: `xxhash-rust` + ~100 LOC of allocation logic.

**Tool paths** are **not** restricted to the workspace: tools accept **absolute or workspace-relative** paths (relative resolves against the workspace root) — the agent can read and edit anywhere on the host filesystem in v0 (no sandbox; that is the security-model fog, #13/#10).

### 5.5 Agent types

An **agent type** is a named configuration: system prompt + tool subset + model override + optional default context mode. One built-in **`general`** type (inherits the session's tools/model) is always present; user types are **`.md` files with frontmatter** (`name`/`description`/`tools`/`model`/default context mode; body = system prompt), discovered hierarchically: **`~/.config/tau/agents/`** (system) and **`{project root}/.tau/agents/`** (project **wins** on name collision, #10).

## 6. Provider contract

(research #4 → #7 → ADR-0003, revised 2026-09-16)

- **OpenAI-compatible endpoints only.** No Anthropic-native, no OAuth/subscription login, no maintained provider catalog, no OS keychain. Rationale: one API surface keeps the core minimal (ADR-0003).
- **v0 speaks `responses` only** — `POST {base}/v1/responses` with streaming — and has **no chat-completions implementation at all** (user decision, 2026-09-16; the per-provider chat-completions fallback that research #4 recommended is **post-v0**). Fidelity per server is the **user's responsibility**: no auto-detection, no probing, no per-provider capability profiles. (OpenAI/OpenRouter/vLLM are native; llama.cpp via its `/v1/responses` shim; Ollama's non-stateful flavor is fine because **tau is client-side stateful** — sessions live in its own files, not the server's.)
- **A provider is a named entry**: `base_url`, `key` (from an **env var or a 0600 config file**), and a list of **model ids**. Commands: list / add / set / delete (#10).
- **Transport** (research #4 recommendation, standing): a **hand-rolled client in `tau-core`** — `reqwest` + an **in-tree SSE frame parser** (~100 LOC: UTF-8-safe buffering, `\n\n` event splitting, `data:` concatenation, `:`-comment skipping, `[DONE]` termination; **mid-stream `error` events must not terminate the stream or commit a zero-usage success**) + `serde` types for the typed Responses events (`response.created`, `response.output_text.delta`, `response.function_call_arguments.delta/.done`, `response.completed`, `error`). Rejected on the record: `rig` (a framework — exactly the catalog/weight ADR-0003 rejects), `llm` (multi-backend catalog + default-on TUI), `openai-rs` (a name-collision trap — a neuroevolution library, not a client), `async-openai` (OpenAI-proper-shaped; drops the reasoning surface on other servers).
- **Reasoning**: decoded into one internal field via serde aliases over the provider dialects; **in the GUI, reasoning output is viewable and collapsible with a user setting for visible-by-default** (user decision, 2026-09-16). (The dialect mess — `reasoning` / `reasoning_content` / `reasoning_details` / `thinking` — is the client's problem; the internal model has one field.)
- **Resilience**: retry on connection errors / 5xx with **configurable timeout and retry parameters** (user-confirmed #7).
- **Usage**: from the `response.completed` event; per-turn usage feeds the status bar and cost display (§9).

## 7. Message lanes: force / steering / follow-up

(#8 → #10 → #11 composer)

One `send` command carries the lane — **force is a parameter on send, not a separate command** (#10). The GUI composer is **one send button + a 3-way lane selector** (#11):

- **⚡ force** (user-initiated; never automatic, and never available to a parent agent over a child): delivers **immediately** — the in-flight LLM stream is **killed**, the partial output kept as an **interrupted entry**, the in-flight **tool batch is let to complete** (tools are not killed), and the forced message is **delivered at the head of the pending queue** on the next LLM call, alongside the tool results — the model sees both. Already-queued steering/follow-up messages keep their positions.
- **↪ steering**: queued, delivered **at the next opportunity** — the next LLM call (the natural boundary is a completed tool batch / turn point). A running sub-agent receives parent `subagent_message`s on its own steering lane, same semantics.
- **⏭ follow-up**: queued, delivered **after the model finishes its work** (turn end).
- **Turn-boundary coalescing** (#10): when a turn boundary arrives with both a queued user composer message and an arriving child notification, they are **concatenated into one context assembly — notification entries first, the user message last** (the most recent human intent nearest the generation point). One turn handles both, not two.
- **stop** is a separate command (soft interrupt per §5.2: kill stream, keep partial, park).
- The queue is **per session**; the GUI renders it as a **vertical list in two sections — steering (top, “next opportunity”) above follow-up (bottom, “after work completes”)** (#11).

## 8. Core ↔ GUI protocol

(research #13 → #10 → ADR-0006)

- **One shared Rust crate of tagged-union messages** — commands in, events out. Tauri commands/events are **transport #1** carrying those same types; the Svelte side **compiles against the protocol types alone** — there is no richer in-process API (no two-surface drift). A future `tau serve` binary + browser client are transports #2/#3 over the identical types (#13: remote is a transport addition, not a re-architecture).
- **No protocol version field in v0** (pre-v1 is breakable; versioning is added before v1 — this deliberately overrides research #13's version-at-handshake recommendation). **No HITL request/response in v0**: the mechanism (message pair + timeout + default + queuing on disconnect) exists in the protocol shape with **zero live request types**; a future security ticket decides what concrete types come back.
- **State ownership**: the core is the **single owner** of all session/workspace/task state; the GUI is a **stateless renderer, rebuildable from snapshot + event stream** — never the other way around (the rule that makes a second, remote GUI possible).
- **Snapshot** (ephemeral — built on demand at app launch, tab open, reconnect; **never a file**): (1) session metadata (id, workspace, title, created, leaf pointer, model, usage); (2) **entry metadata tree** — id, parentId, type, timestamp, size, first-line preview, status — *no payloads*; (3) the **OM observation log**, the only full-payload piece (bounded ~40k tokens ≈ 160 KB by the Reflector); (4) **live state** — queue, sub-agents + tasks (with resume contracts), turn state; plus the **cursor** (last entry id). A 10k-entry session snapshots in **~1–2 MB**, parseable in single-digit ms; consistency is guaranteed by per-session single-writer.
- **Streaming**: deltas **coalesced at 25 ms** (user-specified); tool output is **idempotent-cumulative, correlated by stable ids** (replace-on-receive — exactly what a lossy network wants, #13); every message carries **workspace + session id** over one multiplexed channel; no shared memory or file watching across the boundary.
- **Reads are paged**: `entries {range}` / `entries-since {cursor}` (a stable entry id is a durable cursor, pi-style). The GUI **virtualizes** — renders only the current page + scroll buffer, unmounts the rest; **sidecar blobs stream on card expansion**; archived spans render as collapsed summary blocks.
- **Identity**: a **workspace object** (`id`, `name`, `cwd`-on-host) — **no local paths as identity** (tool args are absolute or workspace-relative paths on the host, §5.4).
- **Commands** (settled #10): `workspace open` · `sessions list / new / open / close / delete / fork / branch / snapshot / entries` · `message send {force?} / stop` · `subagents types / list / state / spawn / message / stop / resume` · `tasks create / update / assign / evidence / cancel` · `providers list / add / set / delete` · `files read`. (fork/branch create a **new branch within the same session file**, not a new session; state commands fold into the session group.)
- **Events** (an open document that narrows as features finalize; seven groups): **turn** (stream deltas, tool start/update/end, usage) · **queue** (lane state) · **sub-agent** (all lifecycle transitions of §5.2 **plus the child's full own stream** — the GUI renders children with full parity) · **task** (state machine transitions, evidence) · **om** (observe/reflect activity) · **session** (branch move, compaction, archive) · **system** (workspace, provider, error).
- **Child sessions are ordinary sessions**: openable in a tab, steerable with the same message command, plus branch/force/stop available — full interaction parity (#10).
- **Performance bar** (the user's biggest gripe with existing tools — GUI lag on large sessions): a **10k-entry session plus two live child streams with no visible lag** is a property of the *protocol* (snapshot size, paged reads, virtualization, 25 ms coalescing), demonstrated by the #11 prototype and a hard acceptance criterion for the build.
- **Remote deferrals** (kept cheap by the above, #13): the `tau serve` binary, auth/TLS, multi-client policy, session sync/replication, latency-specific UX, wire-protocol migration.

## 9. GUI information architecture

(#11 — prototype at [`prototype/gui-ia/index.html`](../prototype/gui-ia/index.html); earlier A/B/C variants preserved on branch `prototype/gui-ia-variants-a-c`)

- **Chat is always central.** A **focus mode** hides both side panes for a clean chat-only view. The transcript renders **markdown + syntax highlighting** with code segments protected from inline formatting, and entries are **virtualized with measured row heights** (no clipping, no oversized gaps).
- **Open workspaces = tabs on top**, with a **`+`** to open a folder (selecting/creating a workspace, §8 identity). The active session opens in a center tab; a child session opened from the tree gets a breadcrumb in the center header.
- **Left pane — tabbed `files` | `sessions`**:
  - `files`: the workspace **file tree**, nested and collapsible.
  - `sessions`: the **session tree, MRU-sorted**; sub-agent sessions grouped under their parent as **collapsible nested groups** (active session expanded by default, others collapsed); a **session archive** folder at the bottom (manually archived zstd sessions, §3). **Badges: a top-level session shows `running` only while the model is actively generating or a sub-agent is running — inactive top-level sessions are untagged; sub-agent sessions keep their full status tags** (running / idle / failed / stopped / done, §5.2).
- **Right pane — tabbed `tasks` | `sub-agents`** (tabs chosen over stacked, user decision 2026-09-17):
  - `tasks`: **collapsed rows, filterable by status (default: not-done), sorted by most-recently-modified**; click-to-expand into a **detail with labeled sections** — steps (with expected outputs) / acceptance criteria / evidence / blocker / resume contract.
  - `sub-agents`: a **tree** (nesting supported; single-click selects, double-click opens the session), same filter pattern.
- **Steering queue** — vertical, two sections: steering (top, “next opportunity”) above follow-up (bottom, “after work completes”), §7.
- **Composer** — one send button + **3-way lane selector** (⚡ force / ↪ steering / ⏭ follow-up), §7.
- **Reasoning** — viewable and collapsible in the transcript; a user setting controls visible-by-default (§6).
- **Status bar** (lualine-style, bottom): `[ workspace · session · state ] [ axis + hints · focus · current lane ] [ 10k render range · render ms · streams · model ]`.
- **Acceptance bar** (non-negotiable, #11): the 10k-entry stress session plus two live 25 ms-coalesced child streams with **no visible lag** — the §8 protocol rules are the mechanism.

## 10. Context files and system prompt

Settled so far: the **system prompt of a session comes from its agent type** (built-in `general` or a `.md` type, §5.5); **a sub-agent's prompt is its own** — its type's system prompt + context files + the delegation brief — never an inherited parent conversation (the `fresh` default, §5.1); context files ride along with the type.

**Context files follow pi's pattern** (settled 2026-09-17, resolving the former U1): load **`AGENTS.md` or `CLAUDE.md`** from `~/.config/tau/` (global), from parent directories walking **up** from the workspace cwd, and from the cwd itself — all layers **appended** to the system prompt; a per-directory **`AGENTS.override.md`** replaces that directory's `AGENTS.md`/`CLAUDE.md` (files from other directories still layer); a `--no-context-files`-style disable.

## 11. Security model

- **No security model in v0** (pi-style): no permission popups, no confirmation dialogs, no trust flow. Tools execute with the user's privileges; **bash danger is accepted as the user's** (research #5: the industry answer is containerization, not popups — and a containerized deployment of tau is trivially possible since the core is a library).
- **No sandbox**: tools act on the whole host filesystem (absolute or workspace-relative paths, §5.4).
- **Keys**: provider keys live in **env vars or 0600 config files** — **no OS keychain in v0** (#7).
- **Child output is untrusted**: marked as such before the parent model reads it; the one enforced boundary (research #5, §5.1).
- **The door is open, not open**: the protocol carries the HITL request/response *shape* with zero live request types, and `tau serve`'s auth/TLS ships with the server — a future security ticket decides what comes back (§8, #13, #10).

**UNRESOLVED**: the concrete security model (sandboxing, tool allow/deny, server auth) — explicit map fog.

## 12. Configuration

- **System-level: `~/.config/tau/`** — providers (named entries, §6), agent types (`agents/`, §5.5), no-project sessions (`sessions/`, §3), and settings: OM thresholds + the **global `om_model`** (Observer 30k / Reflector 40k / buffer 6k, §4), sub-agent caps (concurrency default unlimited / depth default 1, §5.1), request timeout + retry parameters (§6), the 25 ms coalescing constant, the reasoning visible-by-default setting (§6/§9).
- **Project-level: `{project root}/.tau/`** — `agents/` (project types win on collision), `sessions/`, `tasks/` — **one convention for all project-local tau state** (user-confirmed 2026-09-17).
- **No OS keychain; no provider auto-detection** (#7).

**UNRESOLVED**: the config **file format** (TOML vs JSON vs JSON5) and the exact key layout — a mechanical choice to make at build time, no design consequence.

## 13. Packaging

(settled at charting, #1)

- **Tauri 2.11 stable**; one **single binary** (the GUI binary embedding `tau-core`, §2).
- **Platforms: macOS first, Linux second; no Windows in v0.**
- **Distribution**: v0 = direct download (dmg/zip) — **no auto-update, default signing only**; **by v1: package managers** (e.g. Homebrew tap, apt, flathub) with an update channel (settled 2026-09-17).

**UNRESOLVED**: app name, icon, and macOS notarization specifics — packaging fog, no architectural consequence (distribution channel settled: direct download in v0, package managers by v1).
