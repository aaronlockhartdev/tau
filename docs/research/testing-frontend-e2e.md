# Research: Svelte 5 frontend testing + E2E tooling (2026, primary sources)

Researched 2026-09-30, in response to the agreed direction: component tests via testing-library on the existing vitest+jsdom, coverage targeting 80%+ (no hard CI floor), a new linter (none today), E2E breadth expanded with a deterministic OpenAI-compatible mock LLM endpoint, and WebdriverIO kept as the E2E driver (user decision 2026-09-24, `docs/research/tauri-ci.md` §4).

**Short answer.** Everything in the agreed direction is adoptable on the current stable versions — with one material correction: the app's Rust core speaks the **OpenAI Responses API** SSE dialect (`response.*` events), not the chat/completions `choices[].delta.tool_calls` dialect the direction assumed. The mock LLM must be built to the dialect the client actually consumes. For linting, **Biome's Svelte support is experimental** (flag-gated, one rule ported, a formatter regression in the current 2.5.14 release) — **ESLint 10 + the official `eslint-plugin-svelte`** is the only stable Svelte 5 linting route.

---

## 1. Svelte 5 component testing

**`@testing-library/svelte` is the current package; `svelte-testing-library` is dead.** The npm `svelte-testing-library` package (last release 1.6.0, 2019-05-18) carries an explicit deprecation notice in the registry: "🚨 svelte-testing-library has moved to @testing-library/svelte. Please uninstall svelte-testing-library and install @testing-library/svelte instead." (npm registry metadata, https://www.npmjs.com/package/svelte-testing-library; the notice links testing-library/dom-testing-library#260). The current package `@testing-library/svelte` is at **5.4.2** (published 2026-06-23, npm registry https://www.npmjs.com/package/@testing-library/svelte), released from the monorepo `testing-library/svelte-testing-library` (`packages/svelte` + `packages/svelte-core`), last pushed 2026-09-07 (GitHub repo https://github.com/testing-library/svelte-testing-library).

**Svelte 5 runes support is first-class.** `@testing-library/svelte@5.4.2` peer-depends on `svelte: "^3 || ^4 || ^5 || ^5.0.0-next.0"` and `vitest: "*"` (npm registry metadata). The official docs example is written in runes (`let { name } = $props()`, `let showGreeting = $state(false)`) — https://testing-library.com/docs/svelte-testing-library/example. The render core builds on Svelte 5's imperative `mount` API (`packages/svelte-core/src/render.js` → `mount.js`, https://github.com/testing-library/svelte-testing-library/blob/main/packages/svelte-core/src/render.js), and the current release line is full of runes-specific fixes: 5.4.2 "separate runes and non-runes wrapper scaffold", 5.4.0 "add wrapper option", and the `svelte-core` 1.1.1 fix "fix props proxy target to avoid double `$effect` runs" (releases: https://github.com/testing-library/svelte-testing-library/releases).

**The recommended vitest integration is exactly the repo's existing stack.** Official setup docs (https://testing-library.com/docs/svelte-testing-library/setup): dev deps `@testing-library/svelte`, `@testing-library/jest-dom` (optional, "highly recommended"), `@sveltejs/vite-plugin-svelte`, `vitest`, `jsdom`/`happy-dom`; a `vitest-setup.js` containing `import '@testing-library/jest-dom/vitest'`; and the `svelteTesting()` plugin from `@testing-library/svelte/vite` in the Vite/Vitest config alongside `svelte()`, with `test.environment: 'jsdom'`. The `svelteTesting` plugin "adds an automatic cleanup fixture" and "adds `browser` to `resolve.conditions`" (both individually disable-able) — the browser condition is what makes lifecycle callbacks run under jsdom (the FAQ's "Why isn't onMount called" entry, https://testing-library.com/docs/svelte-testing-library/faq).

**Runes test patterns.** Two primary-source caveats shape how runes components get tested:

- Effects do not run during `mount`. The Svelte 5 imperative-API docs state: "unlike calling `new App(...)` in Svelte 4, things like effects (including `onMount` callbacks, and action functions) will not run during `mount`. If you need to force pending effects to run (in the context of a test, for example) you can do so with `flushSync()`" (https://github.com/sveltejs/svelte/blob/main/documentation/docs/06-runtime/04-imperative-component-api.md — the source of the svelte.dev docs page). So `$effect`-driven UI in a test needs `await tick()` / `flushSync()` (and for async settling, `vi.waitFor`) before asserting.
- jsdom's `requestAnimationFrame` is unreliable in Vitest, which affects transition/tween assertions; the official FAQ's workarounds are switching to `happy-dom` or stubbing `requestAnimationFrame` with a 16 ms `setTimeout` (https://testing-library.com/docs/svelte-testing-library/faq).

The `render(Component, componentOptions, renderOptions)` API re-exports all of `@testing-library/dom` queries plus `act` (now async), `cleanup`, and an async `fireEvent`; results include `component` (the Svelte 5 component instance), `container`, `baseElement`, `rerender`, `unmount` (https://testing-library.com/docs/svelte-testing-library/api). `@testing-library/user-event` (current **14.6.7**) is the recommended interaction layer, including `user.upload` for file inputs (example + FAQ pages above). `@testing-library/jest-dom` is at **7.0.1** (npm registry).

> **VERDICT (topic 1).** `@testing-library/svelte` **5.4.2** + `@testing-library/user-event` 14.6.7 + `@testing-library/jest-dom` 7.0.1 on the repo's existing vitest 5.0.2 + jsdom 30 + `@sveltejs/vite-plugin-svelte` 7.3.1. It is the maintained, Svelte 5-native option; `svelte-testing-library` is a deprecated alias. No new runner, environment, or plugin family needed — add the `svelteTesting()` plugin, a jest-dom setup file, and `environment: 'jsdom'` to `app/vitest.config.mjs` (which today has no environment and excludes `tests/e2e/**` only).

## 2. Linting / formatting for Svelte 5 + TS

**Biome's Svelte support is experimental — not a viable linter of record.** `@biomejs/biome` is at **2.5.14** (released 2026-09-16, https://github.com/biomejs/biome/releases). Svelte parsing/formatting exists but is gated behind `html.experimentalFullSupportEnabled: true` (the config key named in the 2.5.14 regression report, https://github.com/biomejs/biome/issues/11836). The Svelte *lint* rule set is still being ported: the tracking issue "port eslint-plugin-svelte rules" (https://github.com/biomejs/biome/issues/10540, opened 2026-06-02) is open with nearly every rule unchecked — only `require-each-key` is marked done. And the current stable release has a live Svelte formatter regression: 2.5.14's `check --write` rewrites `{@const x = y}` into the invalid `{@const (x = y)}` "silently", regressed from 2.5.13 (issue #11836, filed 2026-09-18, closed completed — i.e. the fix postdates the current 2.5.14 tag). A formatter that can corrupt Svelte files on a routine `--write` is disqualifying for a repo where formatting runs in CI.

**ESLint 10 + the official Svelte plugin is the stable route.** `eslint-plugin-svelte` (**3.23.0**, not deprecated; peer-deps `eslint: ^8.57.1 || ^9.0.0 || ^10.0.0`, `svelte: ^3.37.0 || ^4.0.0 || ^5.0.0`; homepage https://sveltejs.github.io/eslint-plugin-svelte) is "the official ESLint plugin for Svelte", built on `svelte-eslint-parser` (**1.8.1**, https://www.npmjs.com/package/svelte-eslint-parser), both under the sveltejs org (https://github.com/sveltejs/eslint-plugin-svelte). Current stable ESLint is **10.11.0** and typescript-eslint **8.71.0** (npm registry). The plugin README documents flat-config setups for exactly this stack — a TypeScript project config using `@eslint/js` + `typescript-eslint` + `svelte.configs.recommended`, with `.svelte` files routed through the TS parser via `parserOptions: { projectService: true, extraFileExtensions: ['.svelte'], parser: ts.parser, svelteConfig }` (https://github.com/sveltejs/eslint-plugin-svelte/blob/main/README.md). The official preset `@sveltejs/eslint-config` (**10.0.4**) wires the same set: peer-deps `eslint >= 10`, `@eslint/js >= 10`, `typescript >= 5 < 7`, `eslint-plugin-svelte >= 3`, `typescript-eslint >= 8`, `eslint-plugin-n >= 17`, `@stylistic/eslint-plugin >= 5`, `eslint-config-prettier >= 9` (npm registry metadata; https://github.com/sveltejs/eslint-config).

**Fit with repo conventions (2-space, single quotes, semicolons on, no formatter tooling).** Style rules come from `@stylistic/eslint-plugin` (5.10.0), a peer of the preset — quotes/indent/semis are plain stylistic rules, so the conventions are enforceable by the linter itself without adopting Prettier/Biome as a formatter. Note the preset's `typescript >= 5 < 7` peer range: the repo's `typescript` 6.x line fits; the `@typescript/native` 7 (tsgo) alias used for `svelte-check --tsgo` is a separate build-time tool and not the ESLint parser's TS.

One naming trap: the old `svelte-eslint-plugin` package **no longer exists on npm** (registry 404), and `@sveltejs/eslint-plugin-svelte` does not exist either — the official name is `eslint-plugin-svelte` (no scope). The plugin README's CLI on-ramp (`npx sv add eslint`, https://svelte.dev/docs/cli/eslint) targets Svelte projects generally; tau's `app/` has no `svelte.config.js` (Svelte config lives inline in `vite.config.ts`), and the README documents loading that via `@sveltejs/load-config` for `parserOptions.svelteConfig` (same README, "Svelte config inside vite.config.js" section).

> **VERDICT (topic 2).** **ESLint 10.11** flat config + `eslint-plugin-svelte` 3.23.0 (+ `svelte-eslint-parser` 1.8.1) + `typescript-eslint` 8.71.0, with `@stylistic/eslint-plugin` carrying the 2-space/single-quote/semicolon conventions; optionally via the `@sveltejs/eslint-config` 10.0.4 preset. Biome 2.5.14 can lint the `.ts` files but its Svelte parser/formatter is experimental and its current release has a file-corrupting Svelte formatter regression — rejected for `.svelte` files. CI: a `lint` step in the `frontend` job (eslint is a Node dev dep; no new system deps).

## 3. Coverage for Svelte

**`@vitest/coverage-v8` (5.0.2) is the default and the accurate option.** Vitest's config reference: `coverage.provider` is `'v8' | 'istanbul' | 'custom'` with **default `'v8'`** (https://vitest.dev/config/coverage). The guide is explicit about the historical accuracy gap and its closure: "Since v3.2.0 Vitest has used AST based coverage remapping for V8 coverage, which produces identical coverage reports to Istanbul. This allows users to have the speed of V8 coverage with accuracy of Istanbul coverage. By default Vitest uses 'v8' coverage provider" — listed as the "✅ Recommended option to use" with "No pre-transpile step" (https://vitest.dev/guide/coverage). The `@vitest/coverage-v8` package README confirms it "supports native code coverage via v8" and is the provider to leave unset (https://github.com/vitest-dev/vitest/blob/main/packages/coverage-v8/README.md).

**How .svelte files get instrumented.** The V8 provider collects coverage at runtime from the executed (transformed) module and then "remaps coverage results to source files" (guide page above, V8 Provider pipeline). In a vitest run, `.svelte` files are compiled to JS by `@sveltejs/vite-plugin-svelte` inside the same Vite transform pipeline that serves the test, with source maps — so the remap lands coverage on the original `.svelte` source. This is the same mechanism any Vite-compiled language relies on; there is no Svelte-specific coverage plugin in the official stack.

**Exclusion config for tau's layout.** Coverage scoping is glob-based: `coverage.include` (default: "files that were imported during test run") and `coverage.exclude` (glob list, "matched against each file's path relative to the project root"; https://vitest.dev/config/coverage). For an 80%-of-what-matters target: `include: ['svelte/**/*.{ts,svelte}']` and keep the default import-driven collection, or add `all: true` semantics via include globs. `tests/e2e/**` is already outside vitest's collection (`test.exclude` in `app/vitest.config.mjs`), `svelte/scripts/**` (the protocol-parity script) drops out of the include glob, and `.svelte-check/` is a generated type-check cache — it never matches a source include glob and needs no explicit entry. If transpiled artifacts ever leak into the report, `coverage.excludeAfterRemap` ("Apply exclusions again after coverage has been remapped to original sources… Use this option when you are seeing files that show up in report even if they match your coverage.exclude patterns") is the documented remedy (same reference page).

> **VERDICT (topic 3).** `@vitest/coverage-v8` **5.0.2** (the default provider — nothing to configure beyond a `coverage` block with an `include` scoped to `svelte/**`). Istanbul is functionally equivalent post-remapping since vitest 3.2 and slower; no reason to choose it. Run with `vitest run --coverage` locally / in the `frontend` CI job as a *reported* number (text reporter), with the 80%+ target tracked but not gated (per the agreed "no hard CI floor").

## 4. WebdriverIO + Tauri E2E

**The repo's architecture is exactly the current official one.** The Tauri v2 WebDriver guide (https://v2.tauri.app/develop/tests/webdriver/): "The recommended way to use it with Tauri is WebdriverIO and the @wdio/tauri-service, which works on Windows, Linux, and macOS. Maintained under the WebdriverIO project, it provides Tauri API access through `browser.tauri.execute()`, command (IPC) mocking, frontend and backend log capture, and multiremote. By default the service runs an embedded WebDriver server inside your app, so no external driver is needed on any platform — and this is how macOS is supported." It names the two plugins tau already registers behind its debug-only `e2e` cargo feature: `tauri-plugin-wdio-webdriver` (embedded server) and `tauri-plugin-wdio` (execute/IPC-mock/log-capture), plus a browser mode for renderer-only tests. tau's `wdio.conf.mjs` (embedded provider, debug binary, Vite dev server as devUrl, log capture on) matches this shape point for point.

**The CI guide matches tau's workflow.** https://v2.tauri.app/develop/tests/webdriver/ci/ : run `cargo test` before the WebDriver tests "to avoid testing a broken application"; on Linux install `webkit2gtk-driver` **and** `xvfb` in addition to the build libs (the driver ships in a separate package from `libwebkit2gtk-4.1-dev`); run the suite under `xvfb-run` on Linux. tau's `ci.yml` does all three on both the `macos-acceptance` and `linux-acceptance` jobs.

**`@wdio/tauri-service` 1.4.0 is current and WebdriverIO-maintained.** npm release 1.4.0 (2026-09-06, https://www.npmjs.com/package/@wdio/tauri-service) from the `webdriverio/desktop-mobile` monorepo (`packages/tauri-service`), i.e. the WebdriverIO org owns it — the same home as the runner. Service capabilities (README, https://github.com/webdriverio/desktop-mobile/blob/main/packages/tauri-service/README.md): automatic binary detection, `embedded` (default, all platforms) / `external` (tauri-driver, Win/Linux) / `crabnebula` providers, per-worker driver spawning, browser mode. The configuration reference (https://github.com/webdriverio/desktop-mobile/blob/main/packages/tauri-service/docs/configuration.md) documents every option tau sets — `appBinaryPath` (must point at the built binary; the old directory-walking resolver was removed for workspace/release-build breakage, #295), `driverProvider`, `startTimeout`/`commandTimeout`, `captureBackendLogs`/`captureFrontendLogs` + log levels, and `tauriDriverPort` where "each worker process gets a unique port (port + worker index)".

**Parallelism.** The service supports it natively: "Per-worker driver spawning for parallel testing" (README feature list) and `maxInstances > 1` "enables per-worker mode automatically" with a separate driver per worker (E2E guide "Per-Worker" section, https://github.com/webdriverio/desktop-mobile/blob/main/docs/e2e-testing.md; configuration reference "Complete Configuration Example" with `maxInstances` / `maxInstancesPerCapability`). On GitHub Actions this means N concurrent app instances + N webviews on one runner (macos-15 ARM, ubuntu-latest). The alternative CI shape is spec sharding across jobs (`--spec` filters / separate `specs:` globs per job), which the runner's config supports directly. Given the user's "nice-to-have, not critical" ranking and this repo's own finding that a starved CI webview is the flake source (`docs/research/tauri-ci.md` §1–2), the safe posture is: keep `maxInstances: 1` in CI (the current setting) and treat parallelism as a local-`just acceptance e2e` or future-optimization item — concurrency on the same runner buys little when the bottleneck is the runner's webview, and it multiplies the exact flake class below.

**Known CI pitfalls (primary sources).** The desktop-mobile repo keeps a running "CI Flake Log" of transient/environmental failures in this exact stack (https://github.com/webdriverio/desktop-mobile/blob/main/docs/ci-flake-log.md):

- **F1 — macOS embedded-provider idle stall (the big one for tau's macos-15 job):** `Error: Script execution timed out`, ~26 s gaps between `runJavaScript` calls on the idle headless run loop; earlier variant "A JavaScript exception occurred (code 4): Completion handler … no longer reachable". Quantified at ~1-in-5 attempt clear rate on the un-pumped path; mitigations tracked in #540 / #549 (code-4 fix) and an in-flight 50 ms `NSTimer` run-loop pump (#553). This is the same wall tau hit in the pilot era, now documented by the stack's own maintainers.
- **Provider scope note:** the WebView2 150 elevated-host regression (Windows, #542) broke the *external* provider's CDP route; "Our embedded Tauri driver is immune" — relevant only if tau ever adds a Windows E2E leg.
- **Debug-builds-only bridge:** the embedded WebDriver endpoint exists only in debug builds (the dioxus-service docs state the bridge is "compiled behind `#[cfg(debug_assertions)]`. Release builds will not expose the WebDriver endpoint"; tau gates the plugins on its `e2e` cargo feature — same principle).
- **Linux:** `webkit2gtk-driver` is a separate apt package from the build deps and must be installed explicitly (Tauri CI guide); the webview needs an X display (`xvfb-run`, tau's current setup).
- **Timing/readyState:** the structural answer remains framework-level waiting (auto-wait, `waitforTimeout`/`timeout`/`connectionRetry*` — tau's conf already carries generous 30 s/60 s/120 s budgets) rather than fixed sleeps; the E2E guide's best-practice list says the same: "Avoid flaky patterns — Use explicit waits, not fixed timeouts" (e2e-testing.md, Best Practices).

> **VERDICT (topic 4).** Keep **WebdriverIO 9.32.0 + `@wdio/tauri-service` 1.4.0, embedded provider** — it is the current official Tauri stack, maintained by the WebdriverIO org, and the repo's config already matches the official docs (architecture, CI ordering, xvfb, log capture, failure artifacts). No tooling change; the open items are breadth (topic 5/6) and, only if CI time becomes the bottleneck, `maxInstances` > 1 locally and spec-sharding across jobs in CI.

## 5. Mock LLM endpoint

### 5a. The wire format the app actually consumes (primary sources)

The direction as stated assumes the **chat/completions** streaming dialect. That dialect does exist and is verified against OpenAI's own fixtures: the openai-python SDK's test suite ships raw SSE bytes "auto-generated from the live API" (https://github.com/openai/openai-python/blob/main/tests/lib/chat/test_completions_streaming.py) — in `choices[].delta`, tool calls arrive as `tool_calls: [{index, id, type: "function", function: {name, arguments: "<incremental JSON string>"}}]` chunks, closing with `finish_reason: "tool_calls"` and `data: [DONE]` (live snapshot, e.g. https://github.com/openai/openai-python/blob/main/.inline-snapshot/external/c6aa7e397b7123c3501f25df3a05d4daf7e8ad6d61ffa406ab5361fe36a8d5b1.bin).

**But that is not what tau's core consumes.** `crates/tau-core/src/provider.rs` (the `Frame` enum, lines 163–201) decodes the **OpenAI Responses API** SSE event dialect: `response.created`, `response.in_progress`, `response.completed` (carrying `response.usage`), `response.output_text.delta`, `response.reasoning_summary_text.delta`, `response.reasoning_text.delta`, `response.output_item.done` (whose `function_call` item is `{id, call_id, name, arguments}` — arguments is a **complete JSON string in one event**, not incremental), `error`, terminated by `[DONE]`, with `:`-prefixed comment lines treated as keep-alives (OpenRouter-style; the `SseParser` doc comment in the same file). The crate header says the provider talks "the `responses` endpoint plus the plain REST endpoints like `/models`".

The Responses API dialect is confirmed by OpenAI's own SDK types, which are generated from the OpenAI API spec: `ResponseTextDeltaEvent.type: Literal["response.output_text.delta"]`, `ResponseOutputItemDoneEvent.type: Literal["response.output_item.done"]`, `ResponseCompletedEvent`, `ResponseCreatedEvent` (https://github.com/openai/openai-python/tree/main/src/openai/types/responses), and `ResponseFunctionToolCall` — `arguments: str` documented as "A JSON string of the arguments to pass to the function", with `call_id` (https://github.com/openai/openai-python/blob/main/src/openai/types/responses/response_function_tool_call.py). OpenAI's official streaming-tools example uses `client.responses.stream(...)` (https://github.com/openai/openai-python/blob/main/examples/responses/streaming_tools.py). The canonical spec page is the API reference for the responses endpoint (https://platform.openai.com/docs/api-reference/responses/create; JS app, not scrapable — the SDK types above are the machine-readable form of that spec).

**Consequence for the mock:** it must speak the Responses API dialect — `response.output_text.delta` for streamed text, `response.output_item.done` + `function_call` for tool calls, `response.completed` + usage, `[DONE]` — because the Rust decoder (and its serde aliases for the reasoning dialects) is built to it. A chat/completions-shaped mock would decode to nothing.

### 5b. Existing OSS OpenAI-compatible mock servers

- **WireMock** (Java; https://wiremock.org, https://github.com/wiremock/wiremock — active, pushed 2026-09-29) — the general-purpose HTTP stubbing standard. First-class SSE support is in its source tree (`wiremock-core/.../message/sse/`: `SseMessageChannel`, `SseSession`, `SendSseMessageActionBuilder`, plus `SseAcceptanceTest`, https://github.com/wiremock/wiremock). It can serve any canned SSE body — but it is a JVM dependency, OpenAI-agnostic (you hand-author every SSE payload), and unrelated to the repo's Rust/Node toolchain.
- **MockLLM** (Python, PyPI `mockllm`; https://github.com/StacklokLabs/mockllm, Apache-2.0) — "mimics OpenAI and Anthropic API formats… predefined responses from a YAML configuration file… Streaming support… Mock token counting" (README). Closest OSS fit on paper, but its response model is text-only: `src/mockllm/models.py` defines `OpenAIDeltaMessage`/`OpenAIStreamChoice` with no tool-call fields, and the README shows only prompt→text mappings. It cannot script the tool-call turns tau's E2E needs, and it adds a Python runtime to the pipeline.
- **Long tail** — `polly3d/mockai` (JS, ~89★), `zerob13/mock-openai-api` (TS, ~32★), `axium-lab/llm-mock` (~24★), `inference-gateway/tokenless` (~2★) (GitHub repo search, 2026-09-30): small community projects, none with primary-source-grade maintenance signals, and none targeting the Responses API dialect with scripted tool calls.
- **`gptcodeproxy`** — GitHub repository search returns **zero results** (2026-09-30); not verifiable, treated as nonexistent for decision purposes.

### 5c. Deterministic scripted transcripts

The repo already owns the right pattern for determinism: hash-pinned `.jsonl` session fixtures (`dogfood/sessions/`, sha256-pinned in `wdio.conf.mjs`), a `canned://` provider scheme, and a one-shot tokio `TcpListener` SSE mock that counts connections (`crates/tau-core/src/provider/tests/server.rs`). Best practice, consistent with all of that:

- **File-driven scenarios:** one committed file per scripted conversation (SSE bodies, or a higher-level scenario JSON the mock expands), under a dedicated dir (e.g. `dogfood/e2e-mocks/`), each **sha256-pinned** in the E2E config exactly like the dogfood sessions — drift fails the run at `onPrepare`, not mid-test.
- **Scenario selection by env** (the existing `TAU_E2E_*` convention): which scenario a given provider/model name maps to, so specs stay declarative.
- **Deterministic outputs:** fixed `id`/`call_id` values (no timestamps/randomness in the wire output), fixed `usage` token counts, lorem-ipsum text at realistic lengths, and a fixed fallback response for unscripted prompts so a spec can't hang the stream.
- **Streaming fidelity:** emit deltas in multiple `data:` frames with small sleeps between writes (the `a_healthy_long_stream_outlives_the_connect_deadline` test in `server.rs` already exercises paced frames) so the E2E actually exercises incremental rendering, not one-shot bodies.

> **VERDICT (topic 5).** Build a **small dedicated Rust mock server** — promote the existing `crates/tau-core/src/provider/tests/server.rs` one-shot SSE pattern into a standalone bin (or a test-support binary) that serves Responses-API-dialect SSE from hash-pinned scenario files. No OSS option speaks the right dialect with scripted tool calls; WireMock is the wrong toolchain; MockLLM can't do tool calls; the long tail isn't trustworthy. A Rust mock reuses the repo's tokio/reqwest stack, adds zero runtime languages to CI, and the scenario files slot straight into the existing hash-pinning + `TAU_E2E_*` env conventions.

## 6. E2E structure for many interaction specs

**The WebdriverIO org's own E2E guide** for desktop services (https://github.com/webdriverio/desktop-mobile/blob/main/docs/e2e-testing.md) is the primary source for structure, and it matches tau's existing legs model:

- **Layout:** specs grouped per functional area (`api.spec.ts`, `dialog.spec.ts`, `logging.spec.ts`, `mock.spec.ts` per framework), shared test utilities in a `lib/` dir, one wdio config per app/provider variant. For tau: keep the single `wdio.conf.mjs` + legs model (it already env-selects `specs: legs.map(...)`); grow `app/tests/e2e/` into per-feature specs (`tree.spec.mjs`, `composer.spec.mjs`, `transcript.spec.mjs`, `archive.spec.mjs`…) plus a `support/` dir for shared fixtures/selectors/convergence helpers, and the mock-LLM scenario files under `dogfood/e2e-mocks/`.
- **Best practices list (verbatim spirit):** "Isolate tests — each test should be independent; Clean up state — reset app state between tests; Use meaningful selectors — prefer `data-testid` attributes; Avoid flaky patterns — use explicit waits, not fixed timeouts; Log strategically; Test user flows — focus on real user interactions, not implementation details."
- **Retry policy:** WebdriverIO v9's runner options include spec-file-level retries — `specFileRetries` ("Count of retry attempts for an entire specfile when it fails as a whole"), `specFileRetriesDelay` (seconds between attempts), and an immediate-vs-deferred flag (https://github.com/webdriverio/webdriverio/blob/main/packages/wdio-types/src/Options.ts, `Options.Testrunner`). This is the in-runner mitigation for the F1-class macOS idle stall: a small `specFileRetries: 1` on the CI replay/mock legs converts the ~1-in-5 clear-rate flake into a same-run recovery without job re-runs. (Local legs can stay at 0 — a flake that clears on retry locally is still a bug to see.)
- **Artifact capture on failure:** tau already does the right thing and should keep it: `captureBackendLogs`/`captureFrontendLogs` + `backendLogLevel: 'debug'` writing into `OUTPUT_DIR` (`target/e2e`), with the CI jobs uploading `target/e2e/**` on `if: failure()` (both acceptance jobs in `.github/workflows/ci.yml`). The desktop-mobile repo's flake log exists precisely because those artifacts are what make the F1/E/C classes diagnosable — the artifacts are the feature, not the cleanup.

> **VERDICT (topic 6).** Extend the existing legs model: per-feature spec files under `app/tests/e2e/` (one per user flow: tree navigation, composer→turn, streaming render, tool-call turn, archive cascade, re-open), a shared `support/` module, hash-pinned scenario files, `specFileRetries: 1` on the CI legs, and the existing log-capture + failure-artifact upload kept as-is.

## Conflicts with agreed direction

1. **Mock LLM wire format (material).** The direction describes the mock as "chat/completions SSE: `choices[].delta.tool_calls` chunks, `finish_reason`, function args as incremental JSON strings". The app's Rust core (`crates/tau-core/src/provider.rs`) consumes the **Responses API** dialect — `response.output_text.delta`, `response.output_item.done` with a whole `function_call` item (complete JSON-string `arguments`), `response.completed`, `[DONE]`. The mock must be built to the Responses API dialect; a chat/completions-shaped mock would decode to an empty turn. (Both dialects are "OpenAI-compatible" — the conflict is which one this client speaks, verified in the client's own decoder and against OpenAI's SDK types generated from the API spec.)
2. **No other conflicts.** `@testing-library/svelte` on vitest+jsdom (the direction's "testing-library") is exactly the current maintained package; the linter direction is tool-agnostic and resolves to ESLint (Biome's Svelte support is experimental — a finding, not a conflict); WebdriverIO is unchanged and matches the current official docs; coverage via the default v8 provider.
